## Record statuses and publication flag

- `confirmed` — утверждение подтверждено имеющимися доказательствами.
- `not-confirmed` — гипотеза проверена, проблема не подтверждена.
- `hypothesis` — наблюдение требует дополнительной проверки.
- `needs-recheck` — ранее проверенный пункт нужно перепроверить из-за времени, изменений сайта или неполных данных.

У каждого FINDING, CHECK и RECHECK выбрать ровно одно значение: `Public: yes` или `Public: no`. `Public: yes` означает лишь допустимость использования при подготовке публичного материала, а не обязанность включить запись в кейс. `Public: no` запрещает перенос на сайт без отдельного пересмотра. Статус проверки и Public flag решают разные задачи: публичное утверждение должно быть подтверждено, даже если запись помечена `Public: yes`.

## Quantitative evidence rules

Любое число снабжать источником, датой или периодом, размером выборки и методикой подсчёта, если она не очевидна. Число, найденное crawler, отделять от числа вручную проверенных URL. Не использовать неподтверждённые KPI.

Не: «На сайте [N] ошибок».

А: «[Инструмент] обнаружил [N] URL с HTTP 404 в выборке [объём/границы]; источник ссылок проверен вручную в DOM [дата], статус целевых URL проверен [способ]». Это условный пример формы записи, а не реальная находка.

## Causality rules

Разделять **наблюдаемое изменение** и **причинное утверждение**. Не писать «SEO-работа увеличила трафик на X%» без достаточных доказательств причинной связи. Если внедрение и измерение подтверждены, допустима ограниченная формулировка: «После внедрения изменения показатель изменился на X% за период Y» с источником, методикой и без автоматического приписывания всего эффекта SEO-работе.

## Confidentiality

Не включать в source-файл пароли, API keys, токены, персональные данные без необходимости, приватные клиентские сведения и закрытые серверные данные, если их хранение в репозитории или публикация не разрешены. Если доказательство чувствительное, описать его существование и способ проверки без копирования секрета.

## Production handoff

`source Markdown → content plan → public Markdown in src/content/ → Astro → HTML`

При переносе в публичный Markdown Codex должен:

- использовать только подтверждённые данные;
- учитывать `Public` flag и отдельный content plan;
- не переносить internal notes автоматически;
- не превращать recommendation в result;
- не превращать hypothesis в fact.

Перед публикацией ещё раз проверить дату, границы доказательств и допустимость раскрытия каждого выбранного пункта.
